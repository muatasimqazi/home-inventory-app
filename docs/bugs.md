3. ✅ Item deleted on location detail page (/items/[id]) and then clicking delete permanntly shows 404 since the item detail no longer exists

4. ✅ Toasts showing up at the top don't show up properly and seem hidden behind the heading
   Two real, separate bugs, both now fixed:
   - Offset: the first pass only set sonner's `offset` prop, which is the *desktop* offset — sonner switches to a separate `mobileOffset` below a 600px viewport, and without it toasts silently fell back to the ~16px default on every real phone, still colliding with the header. Set `mobileOffset` to the same value as `offset` on `<Toaster>`.
   - Background: the toast wrapper (`src/components/ui/sonner.tsx`, shadcn's default template) styled itself with raw `var(--popover)`/`var(--popover-foreground)`/`var(--border)`, but this project's Tailwind v4 setup only ever defined those tokens as `--color-popover`/`--color-popover-foreground`/`--color-border` — every other shadcn component in the codebase reaches them via Tailwind utility classes (`bg-popover`, `border-border`), only this one referenced the bare (non-`--color-`) names directly, which were undefined, so the background fell back to fully transparent, making toasts unreadable against page content. Fixed the variable names to match.
   Verified live at a 390px viewport: toast now renders solid white with correct text/border color, clear of the header.

6. NFC issues

   - ✅ once nfc is written, no way to add more nfc tags or remove exsiting one — added a "Write a different tag" action that unlinks and returns to setup.
   - ✅ shareable link doesn't have the correct url of the website and takes to 404 page — added a real `/c/[token]` route plus a shared URL helper built from the actual deployed origin; a scan while signed out now lands back on the real bin after signing in instead of just "/". While rebuilding the iOS flow below, found this helper (and the Google OAuth redirect, same root cause) was still producing a schemeless URL (`shohaz.muatasim.com/...` instead of `https://shohaz.muatasim.com/...`) whenever `NEXT_PUBLIC_APP_URL` has no scheme, which it doesn't in this env — fixed with a shared `appOrigin()` helper in `src/lib/urls.ts` that normalizes it once.

That turned out to be a genuine dead end, not a bug: **Apple blocks importing unsigned shortcuts** from an arbitrary URL — only shortcuts signed via the real Shortcuts app and shared through iCloud can be imported that way, which nothing running outside Apple's own toolchain (i.e. nothing in this environment) can produce. No code fix is possible here.

Once written with a plain NDEF URL record, **iOS's own OS-level NFC reading (since iOS 11)** opens that link natively on tap — no app, install, or automation needed at all, which is a strictly simpler and more reliable end state than Shortcuts ever was. A "I've written this tag" action marks it linked once done elsewhere. Verified live (iOS user-agent): the old Shortcuts buttons are gone, the new copy-link button puts the correct, now-scheme-complete URL on the clipboard, and marking-as-linked works; the Android write flow was re-verified unchanged.

Note: the *write* flow itself remains a deliberate simulation (unchanged) — real `NDEFWriter` hardware calls are also deferred, since there's no physical NFC device in this environment to verify against, and writing is higher-stakes to get wrong silently than reading.
7. ✅ Add container on location page shows the dialog but the iphone keyboard is infront of it
   The first fix (`interactiveWidget: "resizes-content"`) is a Chromium-only viewport feature — Safari has never implemented it, so on a real iPhone it did nothing at all. iOS Safari resizes the *visual* viewport when the keyboard opens but leaves `position: fixed` elements anchored to the full (keyboard-covered) layout viewport, which is the real, well-known cause. Added a `useKeyboardInset` hook (`src/hooks/use-keyboard-inset.ts`) that tracks `window.visualViewport`'s resize/scroll events (supported on both engines) and lifts the bottom sheet by the resulting gap via an inline `bottom` style — fixes every bottom sheet in the app at once, not just this one. Verified live by mocking a controllable `VisualViewport` and simulating a keyboard open/close: the sheet's `bottom` style tracked the simulated keyboard height exactly and returned to 0 on close. A literal iOS software keyboard can't be triggered in this environment, so the OS-level trigger itself is unverified the way everything else this session has been — but the response logic that would run when it fires is confirmed correct.

   The sheet now opens pre-filled with the real next generated code, still fully editable.
9. ✅ Select photo takes to phone camera app instead of giving option to choose photos

10. ✅ Users/Members have no way to update their names
    Not just missing UI — no RLS policy let a member update even their own row. Added a scoped self-update policy, a store action, and a tappable profile row in Settings.
11. ✅ Items photos are not getting saved to supabase, only shows emoji, which sould be a fallback or users should be able to choose what they want to show as image
    Genuinely missing feature, not a save bug — no schema/storage existed for a real item photo at all; the captured photo was thrown away after AI detection. Added a real column + a public Storage bucket, upload/remove actions, and pickers in the manual-add flow, item detail page, and an auto-attach from capture when there's exactly one photo in the session. Emoji remains the fallback when no photo is set, as requested.
12. ✅ Users should have an option to show bins and items in a bin in a nice table format consistent with our exisiting ui, such as the settings page showing rows
    Added a grid/list toggle on location and container detail pages, reusing an already-built-but-unwired row component for bins and a new one for items (kept the real photo thumbnail there, unlike the generic-icon row style).
13. ✅ Search functionlity is not reliable
    Token matching was OR-based, so a multi-word query like "red mug" surfaced anything containing just one of the words. Now requires every query word to match somewhere before a row is included at all.
14. ✅ Camera scan shows photo selection option but opens the camera app instead
    A different instance of the same pattern as #9, in a different file. The `/capture` live-camera page has its own "Choose from library" button (gallery icon) wired to a hidden file input — but that input had `capture="environment"` hard-coded on it, which forces mobile browsers to skip the OS picker and jump straight to the camera app, exactly as reported. The live camera itself is already handled separately via `getUserMedia`/canvas (the shutter button), so this input's only real job is picking existing photos — the `capture` attribute never belonged there. Removed it; verified live that the input now only has `accept="image/*"` with no `capture` attribute.
15. ✅ After choosing a library photo it only showed the photo with no way to proceed; also wanted the ability to crop a photo when taken or chosen
    The bare preview screen (a plain `<img>` plus Retake/Use Photo) relied on returning straight to the live camera view on confirm — but presenting the OS's native photo-picker sheet over the page can suspend or fully stop the underlying `getUserMedia` stream on iOS Safari, so that return trip could land on a dead camera view. Replaced the plain preview with a real crop step (`react-easy-crop` + a canvas-based `getCroppedImage` util in `src/lib/crop-image.ts`) for both the shutter-captured photo and a library-picked one, and hardened the return path (`returnToLive`) to check the stream's track health and silently reacquire the camera if it died, instead of assuming it survived. Verified live: both paths (shutter and library) show the cropper with working Retake/Use Photo controls and correctly return to a working live view afterward; the crop utility itself verified separately to produce a real sub-region of the source image (correct output dimensions, sampled pixel color from only the cropped region), not a pass-through.
